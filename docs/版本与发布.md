# 版本与发布

OneFrog 有两个发布渠道：**正式版**给所有人用，**测试版**用来先试新改动。

| | 正式版 | 测试版 |
| --- | --- | --- |
| 分支 | `main` | `dev` |
| 版本号 | `v0.1.26` | `v0.1.26-beta.1`、`v0.1.26-beta.2` … |
| 镜像标签 | `latest`（以及 `v0.1.26`） | `beta`（以及 `v0.1.26-beta.1`） |
| GitHub Release | 正式发布 | 标为「预发布（Pre-release）」 |
| 面板提示升级 | 只提示正式版 | 提示更新的测试版，也提示更新的正式版 |

`beta` 镜像始终是两者中最新的那个：发正式版时 `beta` 也会跟着更新，所以装测试版的机器不会落后于正式版。

## 安装测试版

在服务器上以 root 执行（注意安装脚本来自 `dev` 分支）：

```bash
curl -fsSL https://raw.githubusercontent.com/llc370219/onefrog/dev/install.sh | sudo OF_CHANNEL=beta bash
```

- 渠道会记在安装目录的 `.install.env` 里，以后不带参数重新运行安装命令，或在面板里点「立即升级」，都会继续使用测试版。
- 已经装了正式版的机器，执行上面的命令就会原地切换到测试版，账号、设置和数据都保留。
- 也可以在面板「设置 → 关于与更新」里把「更新渠道」改成「测试版」或「正式版」。改完会立刻重新检查。点「立即升级」时，只把官方镜像改成 beta 或 latest。用更早的安装脚本装的机器，第一次切换仍要重新运行一次安装命令，好换上能改镜像标签的升级程序。
- 想在同一台机器上同时保留正式版，给测试版换一个安装目录和端口：

  ```bash
  curl -fsSL https://raw.githubusercontent.com/llc370219/onefrog/dev/install.sh | \
    sudo OF_CHANNEL=beta OF_INSTALL_DIR=/opt/onefrog-beta OF_PUBLISH_PORT=8090 bash
  ```

- 切回正式版：`curl -fsSL https://raw.githubusercontent.com/llc370219/onefrog/main/install.sh | sudo OF_CHANNEL=stable bash`。

## 发布流程

发布由 GitHub Actions 完成，不需要手动打标签：**合并一个修改了根目录 `VERSION` 文件的 PR，就会发布这个版本。** 工作流先构建并推送镜像，成功后再创建标签和 GitHub Release，所以面板不会提示一个镜像还不存在的版本。

1. 日常改动开 PR，**目标分支选 `dev`**，CI 通过后合并。只要不改 `VERSION`，合并不会发布任何东西。
2. **发测试版**：开一个指向 `dev` 的 PR，把 `VERSION` 改成 `v0.1.26-beta.1`，并新增发布说明 `docs/releases/v0.1.26-beta.1.md`。合并后自动发布为预发布版本，镜像标签 `beta`。
3. 测试机（例如 DC2）在面板「设置 → 关于与更新」里点升级，或重新运行安装命令，装上这个测试版并实际试用。有问题就继续修改、合进 `dev`，再发 `-beta.2`。
4. **发正式版**：测试通过后，开一个从 `dev` 指向 `main` 的 PR，在其中把 `VERSION` 改成 `v0.1.26` 并新增 `docs/releases/v0.1.26.md`。合并后自动发布正式版，镜像标签 `latest`，所有正式版安装都会收到升级提示。之后把 `main` 合回 `dev`，保持两个分支一致。

规则：
- `dev` 上的 `VERSION` 只能是测试版号（`-beta.N`），`main` 上只能是正式版号；写错了工作流会报错，不会发布。
- 同一个版本号只发布一次；已经发布过的版本号再次出现会被跳过。
- 修订号 +1 表示一次常规发布；同一版本的测试版从 `-beta.1` 开始递增。正式版发布后，下一轮测试版用下一个修订号（如 `v0.1.27-beta.1`）。
- 也可以手动推送 `v1.2.3` 或 `v1.2.3-beta.1` 标签发布，规则相同，同样需要对应的发布说明文件。
